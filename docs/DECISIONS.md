# Decisions

Record architectural decisions here. Newest last. Format: date, decision, why.

## 2026-11-04

1. **litegraph.js is a feature reference only.** No JSON or node-name compatibility, no ComfyUI compatibility. We use a clean native format. Why: the goal is a complete Swift node graph for many domains, not a port.
2. **Rendering starts with SwiftUI `Canvas`.** Metal only if benchmarks demand it. Why: far simpler, and works on macOS and iPadOS.
3. **Separate SwiftPM packages** (Core, Nodes, UI, Sync, and domain packs). Why: Core must be reusable by a server and by apps with different domains.
4. **`@Observable` and async/await, no Combine.** Why: fewer redraws, Swift 6 concurrency, project style rules.
5. **Command-based mutation, no whole-graph snapshots.** Why: undo, redo, and server change log share one mechanism.
6. **Open, registry-based port types; ports addressed by stable id, not array index.** Why: domain agnosticism and robust links when ports change.
7. **UUID-backed IDs.** Why: safe for offline creation and server merging.

## 2026-11-04 (Phase 1)

8. **Deployment targets are macOS 27 and iOS 27 (iPadOS 27), Swift 6.4 tools.** Why: new app with no legacy users; lets us use current APIs (Mutex, new SwiftUI, Document APIs) without availability checks. Revisit if we ever need to ship to older OS versions.
9. **`TypeRegistry` is a `Sendable` value type, mutated with `register` during setup**, so packs take it `inout` (`register(in: NodeRegistry, types: inout TypeRegistry)`). Why: provably `Sendable` with no locks (a locked class would also work now that `Synchronization.Mutex` is available, but a value type is simpler), and cheap to copy per document.
10. **`PortType.any` is the only type Core defines**; it is a structural wildcard, not domain knowledge. Compatibility is `identical` / `accepted` (type-level `acceptsFrom`) / `converted` (registered pair) / `incompatible`, all directional.
11. **`GraphValue` encodes as a tagged object (`{"type":"int","value":1}`); int and double never convert implicitly.** Why: the legacy `AnyCodable` turned `1` into `true`. Tags keep every case exact, including `Int64` beyond 2^53, `-0.0`, and non-finite doubles (written as `"nan"`, `"inf"`, `"-inf"` strings). Objects use an unordered `[String: GraphValue]`; deterministic files rely on `.sortedKeys` in the document encoder.
12. **`StringIdentifier` protocol** backs `PortID`, `PortType` and `PropertyID` (bare-string Codable, Comparable). Why: removes copy-pasted boilerplate.
13. **`Graph` mutators are internal; only `GraphEditor` (Core) mutates.** Why: enforces "every mutation is a command" at compile time for UI, Nodes and Sync, which are separate packages. Graph primitives don't check connection rules; `ConnectionValidator` does. Tests use `@testable`.
14. **`Graph` encodes nodes, links and groups as ordered arrays**, not dictionaries (`OrderedDictionary` would encode as a flat key/value array). Duplicate ids fail to decode.
15. **The group type is `NodeGroup`**, to avoid clashing with `SwiftUI.Group` in the UI package. Group membership is derived from bounds, not stored.
16. **Core has its own `GraphPoint`/`GraphSize`/`GraphRect`** so it never imports CoreGraphics (Linux).
17. **Link lookups scan all links for now.** Add adjacency indexes in `Graph` if the 10k-node benchmarks (Phase 2/4) need them; the query API (`links(from:)`, `links(into:)`, `links(attachedTo:)`) won't change.
18. **Validation is rule-based and pluggable per domain.** `ConnectionRule` (one proposed link) and `GraphRule` (whole graph) are protocols; `ConnectionValidator` and `GraphValidator` run ordered rule lists. Core ships structural rules (`ConnectionRules.standard`); a pack adds rules or drops ones that don't apply (a state-machine domain removes `noCycle`). Why: robotics and video editing allow different connections, and rules must be swappable without touching Core.
19. **Validation output is structured, not strings.** `GraphDiagnostic` has severity, an open `DiagnosticCode`, message, and node/port/link references; rules carry an `id` and one-sentence `summary`. Why: an editor, an importer, and an LLM generation loop all need to act on the same findings and describe the active rules. Warnings don't block a connection.
20. **Rules run together and must tolerate missing nodes and ports**; `EndpointsExist` reports those. Why: lets one pass report every problem, which is what a generator needs to self-correct in one round.
21. **Replacing a link is an outcome, not an error.** `ConnectionCheck.replacedLinks` lists links displaced by single-link ports; `GraphValidator` instead flags such a port as `connection.tooManyLinks` in an existing graph.

### Future: LLM-generated graphs (not yet scheduled)

Direction from the project owner: LLMs should generate graphs or the artifacts a graph needs, under domain-specific rules. Groundwork so far: Codable definitions, structured diagnostics, rule summaries. Expected follow-ups, to be scheduled when we reach Phase 5/6:
- A schema export (node types, ports, types, properties, active rule summaries) an LLM prompt can consume. Likely needs a `summary` text on `NodeDefinition`, `PortDefinition` and `PropertyDefinition`.
- A friendlier authoring format than the tagged `GraphValue` JSON and raw UUIDs: short local aliases for node ids, resolved to UUIDs on import.
- Generation as a command batch applied through `GraphEditor`, validated before commit, with diagnostics fed back for repair.
22. **`GraphEditor` is a non-`Sendable` final class**, owned by one actor (UI model on the main actor, runner on its own). Why: gestures and undo need synchronous apply; an actor would force `await` everywhere. Change streams (`changes()`) are `Sendable`-safe and independent per call, backed by a `Mutex`-protected broadcaster.
23. **Commands are labelled, `Codable` data with absolute values.** Positions are set absolutely (not by delta) so undo is exact in floating point. Add commands carry an optional `index`, so undoing a removal restores storage order and the file stays diff-stable. `removeNode` cascades to attached links. Batches apply atomically on a copy of the graph.
24. **Two validation levels (`EditValidation`).** `.full` (default) checks node types, property values and connection rules; `.structural` only checks that referenced nodes/links/groups exist, for undo, redo and server replay of already-validated changes. `addLink` refuses to silently displace a link; `connect(_:)` builds the remove-then-add batch.
25. **Coalescing is explicit.** `GraphCommand.coalesced(with:)` merges commands on the same target (same node set for positions, same node+field, same node+property, same group); `GraphChange.coalesced(with:)` keeps the earliest inverse. The undo manager decides when to call it.
26. **`Node.properties` encodes as a JSON object keyed by property id.** A `[PropertyID: ...]` dictionary otherwise encodes as a flat key/value array in unspecified order, which broke deterministic output.
27. **Undo/redo is `GraphHistory`, a Core class wrapping `GraphEditor`; the platform `UndoManager` is bridged in the UI package.** Why: Core must stay UI-free and Linux-buildable. Edits go through `history.perform`/`connect`/`group` to be recorded; direct editor edits (for example from a server) aren't, and if they break a recorded step, undo/redo throws and clears the history.
28. **Coalescing is opt-in per edit plus an explicit seal.** `perform(..., coalescing: true)` merges into the previous step only if the commands target the same thing and `endCoalescing()` hasn't been called; the UI calls it when a drag or slider gesture ends. Any other edit, undo or redo also seals. Why: time-based merging is non-deterministic and hard to test.
29. **Group membership is derived: a node belongs to a group when its whole frame lies inside the group bounds** (unknown node types count as points). A group inside another group's bounds is nested; groups with identical bounds are not. Why: nothing to keep in sync, and dragging a node out of a group needs no extra command.
30. **Moving a group uses `GroupMove`, captured when the drag begins.** Every update is `originals + total delta`, so members stay fixed during the drag and there is no float drift. The result is a batch of `updateGroup` and `setNodePositions`; batches coalesce when every pair does, so a drag is one undo step. Resize is a plain `updateGroup`. Group bounds must be finite with positive size (`invalidGeometry`).
31. **Documents migrate on a generic JSON tree before typed decoding.** `MigrationChain` runs `DocumentMigration` steps (`from` -> `from + 1`) over `JSONValue`, so typed models only ever know the newest format. A file at the current version skips the tree and decodes directly. Newer-than-supported and unmigratable versions throw `GraphDocumentError`; they are never guessed at. `JSONValue` keeps `Int64` exact.
32. **Deterministic output = sorted keys + ordered arrays + pretty printing by default.** Saving an unchanged document yields identical bytes.
33. **Unknown node types load as ordinary nodes; nothing is dropped.** A `Node` already carries its type id, properties and position, and links address ports by name. `missingNodeTypes(in:)` reports them, and `NodeRegistry.addingPlaceholders(for:)` synthesizes display-only definitions (ports from existing links, `.custom("unknown")` properties) so editors and validators work. Placeholders never replace real definitions.
34. **Format stability is guarded by an inline golden file, not swift-snapshot-testing.** One fixed-UUID document must encode to the exact golden text and the golden text must decode back to it. Why: no new test dependency for a single snapshot. Revisit if we need many snapshots. A format change means bumping `documentSchemaVersion` and adding a migration.

## 2026-11-04 (Phase 2)

35. **`ExecutionPlan.compile` is Kahn's algorithm with a min-heap on storage position.** Same graph, same plan, always; ties never depend on hashing. It also yields `levels` (longest-path depth) so the runner can run a level concurrently. Cycles are found with an iterative Tarjan and reported as components, excluding nodes merely downstream of a cycle, so errors point at the actual loop. Both passes are iterative; a 10,000-node chain and a 10,000-node ring are tested.
36. **Feedback is a node trait, `NodeDefinition.isFeedback`.** Links leaving a feedback node don't order execution and are listed in `ExecutionPlan.feedbackLinks`; they carry the previous evaluation's value. A loop is legal only if some node in it is a feedback node. Why: delay/memory nodes are the standard way to close a loop (PID integrators, video recursion) without making evaluation order ambiguous.
37. **The plan covers the whole graph and ignores node mode and port kind.** Muted/bypassed/never nodes and trigger-versus-data flow are the runner's job (later Phase 2 items); both link kinds order execution. Partial plans (only the upstream of chosen outputs) are not built yet.
38. **Executors live in `NodeRegistry`, beside the definition, not inside `NodeDefinition`.** `register(definition, execute:)`; re-registering without `execute` clears the old one. Why: definitions stay `Codable`/`Hashable` data, so they can be exported as a schema (LLM prompts, server) and displayed without being executable (placeholders have none). Cost: `NodeRegistry` is no longer `Hashable`.
39. **`NodeContext` is an immutable `Sendable` struct built by the runner.** Inputs are linked values over data-port defaults; properties are node overrides over definition defaults. It also carries `ExecutionTime` (tick/elapsed/delta, so deterministic runs can inject a fixed delta), a type-keyed `ServiceContainer` for shared resources, a swift-log `Logger` tagged with node and type, a progress sink, and `checkCancellation()`.
40. **`NodeInvocation.run` never throws.** Errors become `.failure(NodeFailure)`, `CancellationError` becomes `.cancelled`, and a node cannot abort the run. Outputs for undeclared ports are a failure, which catches typos in node implementations. Timing uses `ContinuousClock` around the executor only. `GraphValue` gained strict typed accessors (`intValue`, `doubleValue`, ...) plus `numberValue`, which accepts int or double.
41. **`GraphRunner` is an actor that evaluates in passes ("ticks"); modes are drivers over one `evaluate`.** `step()` is one pass; `run(_ mode:)` streams `TickResult`s for `.once`, `.continuous(interval:)`, `.eventDriven` and `.deterministic(fixedDelta:ticks:)`. Cancelling the consuming task ends the run. Why: one evaluation path means one set of semantics for every mode. Continuous and event-driven streams keep only the newest result if the consumer lags; once and deterministic never drop.
42. **Passes are serialized.** The actor is re-entered while nodes are awaited, so overlapping `step()` calls are chained through `inFlight` and never interleave. Cancelling a pass marks unreached nodes `.cancelled` (`TickResult.wasCancelled`).
43. **Concurrency: nodes in one plan level run in a `TaskGroup`; deterministic mode runs nodes one at a time in plan order** and uses simulated time (`elapsed = tick * fixedDelta`, `delta = fixedDelta`), so a run is exactly reproducible whatever the machine does.
44. **Data flow rules.** A node's input is the linked output from this pass, else the port default. A feedback link delivers the source's output from the previous pass (nothing on the first). An input with several links gets `.array` in link order. A node whose upstream failed, was skipped or cancelled is skipped (`.skipped(.upstreamFailed)`); a failure never stops unrelated branches. A delay node needs no state of its own: it passes its input through and consumers read last pass's output via the feedback link.
45. **`update(graph:registry:)` recompiles and swaps the runner's graph, keeping feedback values of surviving nodes; on a compile error the old graph stays.** A pass in progress finishes on the old snapshot. The runner works on a copy; it never reads the editor's graph.
46. **Event-driven runs coalesce requests** (`requestEvaluation()` buffers at most one pending request). Only one event-driven run should consume the request stream at a time.
47. **Triggers are pulses, separate from data.** A node fires trigger outputs by returning `NodeOutputs(values, triggers:)`; a trigger input fires when any linked trigger output fired in the same pass (previous pass for feedback links). Triggers carry no payload; send data on a data port beside them. `NodeContext.triggered` / `didTrigger(_:)` expose fired inputs. Values may only go to data outputs and triggers to trigger outputs (`wrongPortKind`, `undeclaredOutput` otherwise). Trigger links order execution and, like data links, skip the listener when their source failed. Gating a node on triggers (`onTrigger`) belongs to the node-mode item.
48. **Node modes are applied by the runner, per pass.** `never`: not run, and everything depending on it is skipped (`.disabled`, then `.upstreamDisabled`). `muted`: not run, publishes nothing; nodes after it still run on defaults (`.skipped(.muted)`). `bypassed`: not run; inputs pass to outputs (`.bypassed(outputs)`). `onTrigger`: runs only when a trigger input fired (`.skipped(.notTriggered)` otherwise). `never` and `muted` need no node type, so they work on nodes whose pack is missing.
49. **Bypass pairs ports by type, then order.** Each data output takes the first unused data input that has a value and a matching type (equal, or either side `any`); trigger outputs fire when the trigger input at the same position fired. `NodeDefinition.bypassedOutputs(inputs:triggered:)` is public so UIs can preview it. Bypass works with placeholder definitions, which have no executor.
50. **`onTrigger` nodes latch.** Between triggers the node keeps publishing its last data outputs (`heldOutputs`, cleared by `reset()` and dropped when a node leaves `onTrigger` or the graph); triggers are events and are never held. Before the first run it publishes nothing. An `onTrigger` node with no trigger inputs never runs.
51. **Failure outranks disabled.** If a node has both a failed and a disabled upstream it is `.skipped(.upstreamFailed)`. `TickResult.succeeded` is false whenever any node was skipped or bypassed, so check `failedNodes` to ask "did anything go wrong".
52. **Placeholder definitions only allow several links on an input where some node of that type already has several.** Previously every placeholder input was multi-link, which made single links arrive as arrays and broke bypass.
53. **Dirty tracking is implicit in an exact-input cache, not a set of dirty flags.** A node that declares `NodeDefinition.isPure` is not re-run when its resolved inputs, fired triggers and resolved properties equal the key stored with its cached outputs (`.cached(outputs)`). A property edit, link change or upstream output change alters the key, so it re-runs; downstream nodes re-run only if its output actually changed (early cutoff). Keys are compared for equality, not hashed, so a collision can never return wrong outputs. Cost: every pass still resolves inputs for every node, O(nodes + links); revisit with the 10k-node benchmark.
54. **`isPure` is opt-in (default false).** A wrong "pure" claim silently breaks time-dependent nodes (PID, video), whereas the missing claim only costs speed. Node packs mark pure nodes (math, logic, string). Failures and cancelled runs are never cached. `GraphRunner(caching: false)` disables it.
55. **`update(graph:registry:)` keeps cached outputs for nodes whose type id and `NodeDefinition` are unchanged**, so editing one property re-runs only what it affects. Executors are code and cannot be compared: after swapping an executor without changing its definition, call `invalidateAll()`. `invalidate(_:)` forces specific nodes (outside state a pure node reads changed); `reset()` clears the cache. `TickResult.succeeded` counts cached nodes as success; `cachedNodes` lists them.
56. **Execution state reaches the UI as `ExecutionEvent`s from `GraphRunner.events()`.** Per pass: `passStarted`, then per node `nodeStarted` (only if its executor really runs) and exactly one `nodeFinished(status:duration:)`, plus `nodeProgress`, then `passFinished`. Events carry state, never outputs (those are in `TickResult`), so they stay small. Executed nodes announce start and finish live; skipped, cached, bypassed and cancelled nodes are announced when their level is collected. Events of different nodes in one level may interleave.
57. **`ExecutionState` is a pure reducer over events**, one `NodeRunState` per node (`idle`, `running(progress:message:)`, `finished(status:duration:)`). It keeps each node's last result until the node is reached again, so a continuous run doesn't blank the canvas. The UI's `@Observable` model owns one and applies events; it is not a source of truth for outputs.
58. **Event streams are unbounded by default.** Dropping an event could leave a node showing "running" forever. A consumer that can recover (a UI that only wants the newest state) may pass a bounded policy to `events(bufferingPolicy:)`. Streams only see events sent after they were created, and finish when the runner is released. `Broadcaster<Element>` is now shared by the editor's change stream and the runner's event stream.

## 2026-11-05 (Phase 2, node packs)

59. **Packs conform to `NodePack` (in Core): `static func register(nodes: inout NodeRegistry, types: inout TypeRegistry)`.** Registries are value types, so both are `inout`. Registering twice is harmless. `NodeGraphNodes` ships `MathPack`, `LogicPack`, `StringPack`, `FlowPack`, `UtilityPack` and `StandardPack` (all five), plus `StandardTypes` (`number`, `bool`, `string`). Each pack registers the types it needs, so packs compose in any combination.
60. **The `NoCycle` connection rule honours feedback nodes, matching `ExecutionPlan`.** Found by the first pack test: the editor refused to link a delay node's output back into the loop the runner can execute. Links leaving a feedback node no longer count as edges, and a link from a feedback node can never close a cycle. Lesson: packs built on the public API (no `@testable`) are the cheapest check that Core's rules agree with each other.
61. **Port-type conversion is declared but not performed.** `TypeRegistry.registerConversion` only records that a connection is allowed; the runner delivers values unchanged. So the standard packs register no conversions: `number` to `string` must go through `string.format`, `string.parseNumber` and friends, and the editor rejects the direct link. Adding value converters to `TypeRegistry` (applied by the runner on delivery) is open work; do it when a domain pack needs implicit conversion.
62. **Pack conventions.** Type ids are `<category prefix>.<name>` (`math.add`, `util.number`); every pack node has a registered executor, a well-formed definition, and registered port types (tested for all nodes). Nodes are `isPure` unless they read time or outside state (only `flow.every` today). Math errors (divide or modulo by zero, square root of a negative, any non-finite result) are failures, never NaN or infinity, which `GraphValue` could carry but nothing downstream expects. Unlinked inputs use per-node defaults chosen as identities (multiply 1, divide by 1).
63. **Scale audit at 10,000 nodes found and fixed three quadratic costs** (debug build, before to after): whole-graph validation 279 s to under 1 s; connecting two nodes 4.5 ms to well under 1 ms; adding 10k nodes one command at a time 1.5 s to about 0.3 s. Plan compile, runner setup, a cold or cached pass, and encode or decode were already fast (30 to 300 ms). `ScaleTests` keeps limits roughly 10x above today's numbers so an accidental O(n^2) fails CI without flaking.
64. **`Graph` keeps derived link indexes** (by target port, source port and node), so `links(into:)`, `links(from:)`, `links(attachedTo:)` and the new `outgoingLinks(of:)` no longer scan every link. They are rebuilt on decode, never encoded, and ignored by `==` and `hash`, which compare nodes, links and groups in order. Results stay in storage order.
65. **`GraphEditor.apply` no longer copies the graph per command.** Single commands check before they mutate, so they can run in place; a batch that fails part-way is undone by applying the inverses of the steps that succeeded (inverses are exact). Whole-graph validation finds cycles in one pass (`ExecutionPlan.compile`, mapped to per-link `connection.cycle` diagnostics) instead of asking the `noCycle` rule about each link, and re-checks each link through `ValidationContext.ignoredLink` instead of copying the graph. **Rule authors:** use `context.links(into:)`, `links(from:)` and `outgoingLinks(of:)`, not `context.graph.links`, so a rule is correct when it re-checks an existing link.

## 2026-11-05 (Phase 3)

66. **A subgraph exposes ports by binding, not by boundary nodes.** `SubgraphInterface` lists inputs (each feeding one or more inner input ports), outputs (each fed by one inner output port) and promoted properties (each setting one or more inner node properties), all addressed by inner node id plus port or property id. The inner `Graph` is an ordinary graph, so validation, planning and the runner work on it unchanged, and "convert selection to subgraph" can derive the interface from the links that cross the selection. Cost: the editor has to draw boundary pins itself from the bindings rather than from placeholder nodes. A binding left dangling by deleting an inner node is reported by `SubgraphDefinition.problems(nodes:)` but is harmless at run time and heals if the deletion is undone, so inner edits never cascade into the interface.
67. **Instances are ordinary nodes of type `subgraph.<uuid>`.** The definition's `nodeDefinition` is generated from its interface and registered in the editor's `NodeRegistry`, so the UI, validators, connection rules, history and save format need no special case for instances. The type id uses the subgraph's UUID, so renaming never breaks instances. Executors are attached when running instances is built; until then they report `notExecutable`.
68. **Subgraph edits are `GraphCommand`s on the one editor, not a second editor.** New cases: `addSubgraph`, `removeSubgraph`, `setSubgraphInterface` and `inSubgraph(id:command:)`, which applies any ordinary command to an inner graph with the same validation rules. One command enum keeps one undo history, one coalescing rule set, one change stream and one server log across the root graph and every subgraph. Subgraph commands are valid only at the top level (`invalidScope` inside `inSubgraph`). `GraphCommand` is now `indirect`.
69. **Interface changes keep instances consistent in the same undoable step.** `setSubgraphInterface` removes links on instances (in the root graph and in other definitions) whose port is gone or changed kind, and clears instance property values that no longer exist, then records the exact inverse. Renaming labels, reordering, or adding ports touches no links, because ports are addressed by stable `PortID`. A definition cannot be removed while any instance exists (`subgraphInUse`); nothing is deleted implicitly.
70. **`GraphDocument.subgraphs` is an additive field and does not bump the schema version.** It is omitted from the file when empty, so existing files and the golden test keep their exact bytes, and old files load with no subgraphs. Rule: purely additive optional fields keep the version; anything that changes the meaning of existing fields bumps it and adds a migration. `missingNodeTypes` knows about types the document defines itself.
71. **Instances run inside the runner, not through a registered executor.** One pass over one graph is now `PassEvaluator.run`, used by `GraphRunner` for the root graph and recursively for each instance's inner graph; an instance node's executor is built on the spot from its compiled definition. Modes (`never`, `muted`, `bypassed`, `onTrigger`), upstream-failure skipping, events, timing and cancellation therefore apply to instances with no special code. `GraphRunner` takes `subgraphs:` (and `init(document:registry:)`), registers the instance node types itself, and compiles each definition once; a definition whose inner graph has a cycle fails only its own instances.
72. **Port mapping and scoping.** An instance's input values (linked value, else the interface default) go to every bound inner input port, and an instance's trigger inputs fire the bound inner trigger ports. Each promoted property's effective value (the instance's own, else the promoted default) is written over the bound inner node properties for that run only; the stored definition is never changed. Outputs read what the bound inner output port published, including held and bypassed values. `SubgraphDefinition.problems` reports an exposed input that feeds a port also linked inside, since the outer value would silently win.
73. **Instance state is keyed by the path of instance ids from the root.** Two instances of one definition, and two copies of one inner instance reached through different outer instances, never share feedback values, held outputs or caches, even though inner node ids repeat. `GraphRunner.update` keeps state when no definition changed and drops state of removed instances; any definition change clears all instance state. `reset()` and `invalidateAll()` clear it too. Pure nodes inside an instance are cached per instance; the instance node itself always runs.
74. **Failure, cancellation and runaway nesting.** Any inner failure fails the instance with `In "<name>", <type>: <reason>`, so downstream nodes are skipped as usual; inner cancellation cancels the instance. Nesting deeper than 32 instances fails with "nested too deeply", which is how a subgraph containing itself ends. The editor-time guard against creating such a definition is a separate item.
75. **Inner nodes emit no events and report no progress yet.** Events carry a node id, which is ambiguous across instances of one definition. Path-qualified events are future work for the UI's drill-down view.
76. **`NodeExecutionError.failed` shows its text as written.** Found by the first nested run: the failure message was built with `"\(error)"`, which quotes the text, and every level of nesting doubled the backslashes, so a 32-deep message was exponential and the test hung at 10 GB. `NodeExecutionError` now has an `errorDescription` for `.failed`, and `NodeInvocation` already prefers it. Other cases still print as `caseName(values)`.
77. **Convert-to-subgraph and unpack are command builders on `GraphEditor`, not new command cases.** `convertToSubgraphCommand(nodes:name:promoting:in:)` and `unpackCommand(instance:in:)` read the current graph and return an ordinary `.batch` (plus the new ids, for restoring a selection), so undo, redo, coalescing, the change log and `GraphHistory` need nothing new, and a server replays the same primitive commands. Because a batch is built from the graph as it is now, apply it before other edits. Both work in the root graph or inside a subgraph (`in:`).
78. **Conversion derives the interface from the links that cross the selection's edge.** Selected nodes and the links among them move into the definition unchanged. One outside output feeding several selected ports becomes one exposed input with several targets; one selected output feeding several outside ports becomes one exposed output. Port ids come from the inner ports, made unique with `_2`, `_3`. `promoting:` exposes chosen properties and keeps their current values as defaults, so a converted graph runs exactly as before. The instance is placed at the selection's centre. A multi-link inner port that receives links from outside is refused, because one exposed input cannot stand for several links. A selected feedback node whose output leaves the selection changes timing (the instance publishes this pass's value), which is not compensated.
79. **Unpack copies, remaps and rewires.** Inner nodes are copied with fresh ids (so a definition can be unpacked many times), translated so the inner top-left lands on the instance, and given the instance's effective promoted property values; links to exposed inputs and from exposed outputs are rewired to the inner ports; the instance is removed first so its ports are free for the new links. The definition stays, so removing it is a separate, explicit step. Known difference: an unlinked instance input used its interface default, while the unpacked inner port uses its own default.
80. **A library is copied into documents, never referenced at run time.** Importing embeds the definition and its dependencies, so a document opens, runs and saves with no library available (offline, on a server, years later), and a library edit can never silently change a saved document. The cost, duplicated definitions and explicit updates, is handled by provenance rather than by live links.
81. **Provenance is a revision plus a content digest.** `SubgraphOrigin` records the library id, the revision taken and `contentDigest` (64-bit FNV-1a over the deterministic JSON of interface and inner graph, excluding id and origin). Comparing the document copy's digest with the stored one detects local edits without keeping an old copy; comparing revisions detects a newer library version. `SubgraphLibraryStatus` combines them, including `modifiedAndUpdateAvailable`, so UIs can warn before an update discards local edits. A test pins a digest of fixed content: changing the file format moves every stored digest and must come with a migration.
82. **Library revisions bump only when content changes.** `publish` keeps the revision for identical content and uses `n + 1` otherwise, strips any origin, requires every contained definition to be in the library (or the batch), and refuses loops, all or nothing. `publishable(_:)` gathers a document's definitions plus dependencies, dependencies first, and `adoptOriginsCommand` stamps the published origins back so the document reads up to date.
83. **`updateSubgraph` is the whole-definition counterpart of `setSubgraphInterface`.** One command replaces interface, inner graph and origin by id and cleans up instances (links to vanished or re-kinded ports, vanished property values) in the same undoable step; `setSubgraphInterface` now shares that code. Update replaces only the requested definition and adds missing dependencies; dependencies the document already has are not upgraded.
84. **Where a library is stored is not Core's concern.** `SubgraphLibrary` encodes to deterministic versioned JSON (`encoded()`, `decode(from:)`, newer versions refused) and is a value type. A file store and a server store are `GraphStore`-style work in the Sync package (Phase 6).
85. **A reroute point is a link waypoint, not a node.** `Link.waypoints` is an ordered list of graph-space points the drawn link passes through. They change the picture only: execution, validation, plans, caching and the link indexes ignore them, a test proves a routed graph computes the same, and they cost nothing at run time. This differs from the `util.reroute` node, which stays for the different job of passing a value through (a typed or labelled junction a user can select, mute or bypass). Why waypoints: a reroute used only to bend a link would otherwise add a node to every plan and to every 10k-node benchmark.
86. **Waypoints are edited as a whole list by `setLinkWaypoints(link:waypoints:)`.** Inverse is the old list, so undo is exact; edits to one link coalesce, so dragging a point is one undo step; non-finite points are refused. Adding, moving or removing one point is the UI computing a new list (it alone knows which segment of the drawn path was hit). Waypoints travel with their link when a node is removed and restored, when a selection is converted to a subgraph, and (translated with the nodes) when an instance is unpacked. Links recreated at a subgraph boundary, or replaced by `connect`, start with none.
87. **The file form omits empty waypoints** and `decodeIfPresent` reads old links, so the format needs no version bump and existing files and the golden test keep their exact bytes.
88. **Dynamic ports are numbered groups declared on the definition, with the count stored on the node.** `NodeDefinition.dynamicPorts` lists `DynamicPortGroup`s (direction, kind, type, default, minimum, maximum, initial count). A node stores only `portCounts[group]` (omitted from files when it equals the initial count). Ports are named `<group>_<n>` and come after the fixed ports. Tail-only growth and shrinking means a port's id never changes, so links to surviving ports are untouched, and no renumbering is ever needed. Removing a middle port is not offered; unlink it and leave it free.
89. **There is one place that answers "what ports does this node have": `NodeRegistry.definition(for: Node)`.** It returns the definition resolved for that instance (`NodeDefinition.resolved(for:)`), and a definition without dynamic groups is returned untouched at no cost. Connection rules, validation, the runner's input bindings, node contexts, bypass, subgraph bindings and conversion all use it; looking up by type alone still gives the fixed ports. `PortDefinition.group` marks generated ports, and `NodeContext.values(inGroup:)` reads a group's provided values in port order, which is how a variadic executor is written.
90. **`setPortCount` shrinks by removing the links to vanished ports in the same undoable step**, and its inverse restores the count first and then the links in their original order. Out-of-range counts and unknown groups are refused.
91. **Connection-change hooks are declarative, not closures.** A definition is `Codable` data, so it cannot hold a callback. The `keepOneFree` resizing policy covers the case every example needs: after any change to a node's links, keep exactly one free port after the last linked one, never below the initial count or above the maximum. The editor computes the follow-up `setPortCount` commands after the command (including inside subgraphs) and records them in the same change, so undo takes them back together. A closure hook (a registry entry like an executor, returning commands) can be added the same way if a pack needs behaviour the policy cannot express.
92. **Undo replays recorded inverses without recomputing automatic resizes; redo and replay recompute them.** `apply(_:validation:adjustsPorts:)` has `adjustsPorts: true` by default. `revert` and `GraphHistory.undo` pass false, because the recorded inverse already contains the resizes, and recomputing could not restore a count the user had set by hand. A server replaying a logged command recomputes the same adjustments from the same state, so logs stay small.
93. **Whole-graph validation checks port counts** (`node.invalidPortCount`: unknown group, or outside the group's limits). A link to a port beyond a node's count is reported as a missing port.
94. **The editor refuses any edit that would make a subgraph contain itself.** Placing an instance of S inside T is refused (`GraphEditError.recursiveSubgraph`, carrying the loop as ids ending where it began) if S is T or S already contains T somewhere below it. The same check covers `addSubgraph`, `updateSubgraph` (so a library update cannot close a loop) and instances added inside a subgraph, including through batches, in full and structural modes alike, and undo and redo never trip it because they only restore earlier valid states. Diamonds (A contains B and C, both containing D) are fine. For inner edits the check runs before the inner graph is borrowed for editing: reading the other definitions during that borrow is a simultaneous-access violation.
95. **Loops in existing data are reported, not repaired.** `SubgraphDefinition.loops(in:)` and `GraphDocument.recursiveSubgraphs` find loops in a file made by hand or by another tool, and the runner's depth limit (decision 74) still stops a run that reaches one, so a bad file cannot hang the app.
96. **Layout is pure data in graph space, computed from the node and its resolved definition.** `NodeLayout(node:definition:metrics:)` gives the frame, header, body, resize handle and every port position, using Core's `GraphPoint`/`GraphRect`, so drawing, hit testing and link endpoints read one source and it is testable without SwiftUI. Height grows to fit the ports (never smaller than `minimumSize`); collapsed nodes are header-only and attach every link at the header's middle edge. Unregistered types get a frame and no ports.
97. **Sizes that affect geometry (`NodeLayoutMetrics`) are separate from looks (`GraphTheme`).** The theme is plain data with `RGBAColor`s and is cheap to swap; metrics change where things are, so changing them clears the layout cache.
98. **`GraphEditorModel` mirrors the graph and owns the edit path.** The editor is not observable, so the model keeps an observed copy of `graph` (a copy-on-write value) and a `revision`, refreshed after every edit, undo and redo. Selection is pruned to items that still exist. Layouts are cached per node and reused while the node is unchanged; the cache is cleared when a command can change definitions (subgraph commands) and on `refresh()`. Edits applied straight to the editor need `refresh()`.
99. **Camera zoom is set absolutely, anchored at a screen point.** `GraphCamera.setZoom(_:anchoredAtScreen:)` takes the target zoom, so a pinch applies its total magnification to the zoom it started with and cannot compound (legacy defect 13). Zoom is clamped to 0.1...4.
100. **Hit testing uses a uniform-grid `SpatialIndex` over groups, links and nodes, rebuilt lazily after each edit.** Items are registered in every 256-unit cell they touch; items spanning more than 64 cells (big groups) sit in a short list every query checks. Results are sorted by draw order (groups, links, nodes, each in storage order), so the last hit is the topmost. Link bounds are the padded box around their ends and waypoints, so culling never misses a visible link; exact link picking comes with the interaction work. Rebuilding on every edit is O(n); a 10k-node build plus 1000 region queries runs well under the test limits in debug. Revisit with command-driven incremental updates if the Phase 4 benchmarks show drag stalls.
101. **`GraphHistory` stays the source of truth; the platform `UndoManager` is a mirror that triggers it.** `GraphEditorModel.undoManager` (set from SwiftUI's `@Environment(\.undoManager)`) gets one registered action per new history step. Its handler steps the history and registers the opposite action (landing on the manager's redo stack while undoing and back on the undo stack while redoing), so the Edit menu, shake to undo and keyboard shortcuts all work. `model.undo()` and `redo()` go through the manager when attached so the two never diverge.
102. **Core exposes `GraphHistory.recordedStepCount` so a bridge can tell a new step from a merge.** Stack size cannot, once the limit trims it. The counter increases only when an edit starts a new step. A drag or slider sweep that coalesces registers nothing on the manager.
103. **The model turns off `groupsByEvent` on the manager and groups each step itself.** Otherwise two edits in one run-loop turn would undo together while the history undid one. The manager's `levelsOfUndo` is set to the history limit; an action older than the history does nothing. If the history clears itself after a failed replay, the model drops its manager actions.
104. **Link routes are pure geometry (`LinkPath`) shared by drawing, bounds and picking.** Three styles (`LinkStyle`: spline, linear with port stubs, orthogonal) route through the link's waypoints. The model's `linkStyle` picks one; `link(at:tolerance:)` measures distance along the same polyline the canvas draws, and the spatial index uses the path's bounds, replacing the earlier endpoint box.
105. **Level of detail is a pure function of zoom (`LevelOfDetail`).** Full from 0.6 (port labels), reduced from 0.3 (titles and ports), minimal below (flat boxes, straight links, no text). Minor grid lines drop below 0.35 and major lines when they would be under 8 points apart.
106. **The canvas draws in graph space through one transform, from `model.items(in: visible)`.** Order is groups, links, nodes, so nodes cover links. Link colors follow the source port's type color (trigger and selected links have theme colors), and unlinked ports are drawn hollow. Muted, never-run and bypassed nodes are dimmed by the theme's inactive opacity. Free-standing comments are not a separate item: the note node from the utility pack covers them.
107. **Zoom to fit is limited by the zoom range.** `zoomToFit()` frames node frames and groups together; a graph too large to fit at the minimum zoom of 0.1 fills the view instead of shrinking further.
108. **Input is handled by a platform-free state machine, `GraphInteractionController`.** The view feeds it screen points, `InputModifiers` and a `PointerKind`; it never reads the keyboard or SwiftUI. Every behavior is unit-tested by calling `pointerDown`, `pointerMoved` and `pointerUp`. Only `PlatformInput` reads platform state (AppKit modifier flags), and the gesture wiring lives in `GraphCanvasView`.
109. **What a press means is decided once, in a fixed order:** port, node resize corner, node, link (within 6 points), group title bar or resize corner, then empty canvas. A press moves nothing until it travels 3 points, so a click never nudges a node. Selection changes on press (Shift or Command extends and toggles); clicking one of several selected nodes narrows to it on release if no drag followed.
110. **A drag on empty canvas depends on the pointer: mouse and pencil draw a marquee, a finger pans.** Marquee selects nodes that touch it and groups it fully contains, and Shift adds to the selection. A group's body is empty canvas; only its title bar moves it and only its bottom-right corner resizes it.
111. **Drags are one undo step.** Moves, resizes and group moves use coalescing commands, with `endCoalescing` at the start and end. Cancelling (Escape, or a pinch starting mid-drag) undoes that step, so it leaves no history entry. Snap to grid snaps the dragged node (or group origin) and shifts the rest of the selection by the same amount; Option inverts snapping while held.
112. **Link editing rules.** Dragging from an output, or from an unlinked input, draws a link; the candidate port is validated with the real `ConnectionValidator` and shown as accepted or rejected. Dropping on a node body connects to its first port that is accepted. Dragging from a linked input picks the link up (its source stays); dropping on another input is one "Reconnect" step, on its own input is a no-op, and on empty canvas disconnects. Shift-dragging from an output moves all its links to another output as one step. A link released on empty canvas calls `onLinkReleasedOnEmpty`, which the add-node search will use.
113. **Pinch is measured from the start of the gesture.** `magnify(totalScale:anchor:)` takes the gesture's total magnification and applies it to the camera from when the pinch began, so repeated updates cannot compound (legacy defect 13). Starting a pinch cancels any drag in progress.
114. **Keys, menus and toolbar buttons all go through `CanvasCommand`.** A command is plain data run by `GraphInteractionController.perform`, which returns whether it did anything so a key handler knows whether to consume the key. `CanvasKeyMap` (key plus modifiers to command) and the context menus (`CanvasMenuItem`) are pure and tested; the view and the AppKit shim only translate platform events. Commands that edit run as one undo step.
115. **macOS scroll and right-click use a local event monitor, not an overlay view.** SwiftUI has no view-level scroll-wheel or right-click-with-location API outside `ScrollView`. `MacInputMonitor` (AppKit, macOS only, in `NodeGraphUI` as the rules allow) adds an invisible background view that never takes hits, and watches the window's events for ones inside its bounds. Right-click builds a native `NSMenu` from the pure menu description.
116. **Scroll meaning.** A trackpad pans, and zooms about the pointer while Command or Option is held. A physical wheel zooms about the pointer. Zoom stays within 0.1 to 4. Zoom commands (Command +, -, 0) zoom about the view's center.
117. **Right-click selects first.** An unselected node, link or group becomes the selection; a node already in the selection keeps the whole selection so the menu acts on all of it; empty canvas clears it. Collapse and Pin toggle for the whole selection (if any is off, all go on). Delete removes selected links, then nodes (taking their links), then groups, leaving group members in place.
118. **Keyboard shortcuts:** Delete, Escape (cancels a drag, else clears selection), Command-A, arrows (nudge by grid cells, ten with Shift; a selected group carries its nodes and pinned nodes stay), F (zoom to fit), Command +, - and 0. Undo and redo come from the Edit menu through the environment's `UndoManager` (decision 101), which the canvas view now attaches to the model.
119. **Hover is state on the controller, not the model.** `hover` is a node, port or link, cleared during drags and when the pointer leaves. The renderer highlights it with a lighter border, a ring on the port, or a slightly thicker link.
120. **On iPadOS one raw-touch recognizer drives the pointer; the rest of the input is separate recognizers on the same overlay.** `TouchInputView` (UIKit, iOS only, in `NodeGraphUI` as the rules allow) replaces the SwiftUI drag and magnify gestures there, because SwiftUI cannot tell one finger from two or a finger from a pencil. One touch feeds `pointerDown/Moved/Up` with a `PointerKind` taken from the touch type (finger, pencil, or pointer click). A second finger cancels whatever one finger was doing and hands over to `multiTouchBegan/Moved/Ended`; lifting either finger ends it and the other is ignored until all are up. Palm touches beside a pencil are ignored.
121. **Two fingers pan and pinch in one gesture, measured from the start.** `multiTouchMoved(centroid:scale:)` takes totals since the fingers landed, anchors the zoom at the starting midpoint, then pans by how far the midpoint has moved, so the graph point under the fingers follows them and the zoom cannot compound. A stray `pointerUp` while two fingers are down does not end it.
122. **A finger gets bigger targets than a mouse or pencil.** Ports, link picking and the resize corner use twice the reach for touch (`GraphInteractionController.reach(of:)`); the pencil is treated as a precise pointer, so a pencil drag on empty canvas draws a marquee and a finger drag pans. Nothing else about the pencil (double-tap, squeeze) is bound yet.
123. **Long press and secondary click use `UIContextMenuInteraction` with the same menu description as macOS.** The `CanvasMenuItem` list becomes a `UIMenu` (separators become inline groups, checks become `on` state), and right-click on a pointer or trackpad opens it too. Trackpad scroll arrives as a touchless pan recognizer and pans (or zooms with Command or Option); a trackpad pinch comes through a pinch recognizer that ignores finger touches. Pointer hover comes from `UIHoverGestureRecognizer`. Keyboard shortcuts reuse the `onKeyPress` handling, and a touch gives the canvas keyboard focus.
124. **On iPadOS the canvas does not use SwiftUI focus; the overlay view takes keys directly.** This was first done on a guess that the focus system, which turns on with a hardware keyboard, was swallowing touches. That guess was wrong: the stalls turned out to follow how the iPad was connected to Xcode, not the keyboard (a Magic Keyboard's USB-C port is power only, so a cable plugged into it means wireless debugging, and with the cable in the iPad itself, keyboard and trackpad included, input was fine). The change stays because it removes a dependency on SwiftUI focus, but it is unverified on a device. The UIKit overlay is the first responder: `UIKeyCommand`s cover the Command shortcuts (so they also appear in the Command-hold overlay), and `pressesBegan` handles Delete, Escape, arrows and F through the same `CanvasKeyMap`. macOS keeps `onKeyPress`.
125. **A trackpad pinch must be deliberate and must not disturb a click or scroll.** Defensive, not a confirmed cause of the stall in 124. The pinch recognizer is ignored while a pointer button is down, while a scroll is running, and until the scale moves at least 0.03 from 1. `magnify` applies its absolute zoom to the camera as it is now, so a pan that happens during the pinch is kept, and a stray pinch no longer cancels a drag (it is ignored).
126. **Two fingers landing in one event are a pinch from the start.** The touch recognizer used to take the first touch of the event as a single finger and ignore the other, so a pinch panned instead. Found by driving the iPad simulator with a synthesized two-finger gesture.
127. **iPadOS context menus anchor to a small preview around the press.** A `UIContextMenuInteraction` on a view that fills the screen opens at the edge, so the overlay supplies a targeted preview clipped to a patch around the touch.
128. **A node's body shows one widget row per property, chosen from the property's kind.** Bool is a toggle; a number with both limits is a slider and one without is a drag-to-scrub number; strings are text (multiline gets three rows); choices are a combo; colors are a swatch; vectors read-only; custom kinds draw with a pack's renderer (`registerWidgetRenderer(named:)`) or show their value as text. `NodeWidgetProvider` adds non-property rows such as buttons, which call `onWidgetAction`. Rows are laid out by `NodeLayout` below the ports, so a node grows to hold them at every zoom, collapsed nodes have none, and hit testing and drawing share the frames.
129. **Widgets are drawn in the Canvas and edited in place; only the one being edited is a SwiftUI view.** Drawing is cheap and stays in the single `Canvas` pass (full level of detail only). Toggles flip, buttons fire, and combos and colors open a list or swatches on release. A slider follows the pointer from the press, and a number scrubs when dragged (about one step per eight points) or opens a text field when clicked. Text, number and multiline editing use a real `TextField` or `TextEditor` over the row (`WidgetEditorOverlay`), with the text selected so typing replaces it. A press anywhere else commits the edit; Escape abandons it. Numbers are limited to the property's range, and text that does not parse is dropped.
130. **Widget edits are ordinary undoable property commands.** A drag, scrub or color picker sweep coalesces into one step named for the widget ("Set Gain"), a click or typed value is one step, and cancelling a slider or scrub drag undoes it. A value equal to the current one is not recorded. Slider values snap to the step and drop floating point noise (0.1 times 3 is 0.3).
131. **Palette and add-node search are one panel over one `NodeCatalog`.** The catalog is built from the live `NodeRegistry`, so every pack's nodes and every subgraph definition in the document are listed with no registration of their own; placeholders for missing packs (category "Missing") are hidden. With nothing typed the panel browses by category; typing ranks results (name prefix, then a word start, then a substring, then category or type id, then letters in order), every word of the query having to match.
132. **A dragged link filters the catalog to nodes it can end on and fixes where the node goes.** Releasing a link on empty canvas opens the panel at that point with a `PortFilter` of the dragged port: only nodes with a port of the opposite direction, the same kind, and a compatible type (identical before accepted before converted) are offered, each with its best port. The new node is placed so that port lands exactly on the release point, then connected, all with the node as one "Add" undo step. A link the rules refuse leaves the node added without it. `onLinkReleasedOnEmpty` (decision 112) is replaced by `addNodeRequest`.
133. **The panel opens from a double click or tap on empty canvas (400 ms, 16 points), Shift-A, the empty-canvas menu, or `beginAddNode`.** A node added without a link is centered on the point and snaps to the grid when snapping is on. Escape or a press on the canvas closes the panel. The app shell holds the `GraphInteractionController` so a toolbar button can open it.
134. **The app lets the keyboard shrink the canvas.** The demo uses `ignoresSafeArea(.container)`, not all safe areas, so the software keyboard resizes the canvas and the add-node panel (clamped to the view) stays above it; with all safe areas ignored the panel was drawn under the keyboard.
135. **On macOS the canvas leaves scrolling to any scroll view above it.** The event monitor used to take every scroll event inside the canvas, so scrolling the add-node list (or a choice list) panned the canvas instead. It now hit-tests the window at the pointer and, if the topmost view sits inside an `NSScrollView` (what SwiftUI's `ScrollView` is on macOS), lets the event through. Right-click is ignored while the add-node panel or a widget editor is open. A test pins the assumption that a SwiftUI `ScrollView` hit-tests to an `NSScrollView`, so a future SDK change that breaks it is caught. iPadOS did not have the problem, since its overlay recognizers do not cover views above them.
136. **What the inspector shows is a pure function of the selection (`GraphEditorModel.inspection()`), and every edit is a model action.** One node gives its title, color, mode, pin, collapse, position, size, properties (with whether each is still the default) and ports (type, color, link count); several nodes give only what they can all be set to, with "Mixed" where they differ; one link, one group, or nothing (graph counts and validator problems, each selectable) give their own sections. The SwiftUI view only renders it and calls actions (`setTitle`, `setMode`, `setProperty`, ...), which are the same undoable commands as everything else, so the inspector needs no logic of its own and the data is tested without UI.
137. **Inspector text applies when Return is pressed or focus leaves, not per keystroke, so typing a title is one undo step.** A refused edit puts the old text back. Sliders coalesce a sweep into one step. Clearing a property removes the override (back to the default), and a "reset" button shows only for properties that differ. Size is limited to what the ports and widgets need.
138. **The inspector is a separate view the host places.** `GraphInspectorView(model:)` is a `Form`, so the app can show it as `.inspector`, a sidebar or a sheet. The demo app uses `.inspector` with a toggle button. The canvas is not refit when it opens; it just gets narrower.
139. **The canvas keeps the graph in frame until the view is moved by hand.** A macOS window first reports a provisional size and then its real one, and the single fit made at the first size left the graph tiny in a corner. `GraphEditorModel.viewSizeChanged(to:)` now refits on every size change for as long as the camera still equals the one the model last set; the first pan, zoom or drag by the user ends it. Opening the inspector therefore keeps the graph in view too.
140. **Undo needs a visible control for people with only a touch screen.** `GraphUndoControls` (undo and redo buttons that follow `canUndo` and `canRedo` and show the step's name as help) goes through the same model, history and `UndoManager` as the Edit menu, keyboard and system gestures, so all of them agree. The demo shows it in the corner. The iPadOS system gestures (three-finger swipe left to undo, right to redo, three-finger double tap for the menu) work through the same `UndoManager`, but are not verified on a device.
141. **The editor model has a scope: the graph it shows and edits is the root graph or one subgraph's inner graph.** `scopePath` lists the subgraphs entered, outermost first, and `currentScope` is the last. `graph` mirrors that scope's graph, so layout, hit testing, rendering, selection and the inspector work unchanged. Every command the model performs is wrapped in `inSubgraph(id:command:)` when inside a scope, so edits, undo and redo are the same history as at the root. Undoing or redoing an edit made in a subgraph that is not on screen changes it without moving the view. A scope whose subgraph no longer exists (its creation undone) steps out to the nearest level that does.
142. **Core's connect and group move take a scope.** `GraphEditor.connectCommand(for:in:)` and `connect(_:in:)` validate against the subgraph's inner graph and wrap the command; `GraphHistory.connect(_:name:in:)` records it; `beginGroupMove(_:in:)` reads the inner graph; `editedGraph(in:)` and `validationContext(in:)` give the graph and registries for a scope (nil for a missing subgraph). They were root-only before, which made connecting inside a subgraph impossible.
143. **Navigation: double-click or tap an instance (a two-squares mark in its header), Return on the selected instance, or "Open Subgraph" in its menu; leave with Command-[, "Leave Subgraph" in the menu, or the breadcrumb.** Each level remembers its view; a level visited for the first time is fitted. Moving between levels abandons a drag, an open editor or the add-node search, and clears the selection. Inside a subgraph the canvas has a faint tint, the add-node list leaves out the subgraph itself and every subgraph that contains it (they would make it contain itself), and the inspector validates the inner graph.
144. **The breadcrumb reads a snapshot of the path.** SwiftUI can still update a row for a level that has just gone, so the first version, which indexed the live path, crashed on leaving a subgraph (found on the iPad simulator). A test now hosts the view and enters and leaves repeatedly, and fails with the old code.
145. **Not done: editing a subgraph's interface (its exposed ports and promoted properties) from the canvas.** Inside a subgraph you edit nodes, links and groups; the interface still changes only through `setSubgraphInterface` and conversion. A later interface editor belongs with the library and server work.
146. **Copy and paste work on a `GraphFragment`, defined in Core.** A fragment is the selected nodes, the links with both ends among them, the selected groups, and the definitions of any subgraphs the nodes are instances of (dependencies first). It is plain `Codable` data with its own marked, versioned, sorted-key JSON, and carries no ids that mean anything elsewhere. `GraphEditor.fragment(nodes:groups:in:)` cuts one out and `pasteCommand(_:translatedBy:in:)` builds the command that pastes it with new ids, every position, waypoint and group moved by the offset, and missing subgraph definitions added first (one the document already has, by id, is used as is). A fragment with a node type the editor lacks is refused. The command already names its scope, so the model performs it with `isScoped: true`.
147. **The clipboard is a protocol with a system and an in-memory implementation.** `SystemClipboard` writes the fragment under its own type and as its JSON text, so it pastes between windows and documents, and into a text editor or a note, and a graph written by a tool can be pasted in. `mayHaveFragment` never reads the contents or asks permission, so a menu can enable Paste cheaply; reading is the real test. Tests use `InMemoryClipboard`, so they never touch the developer's clipboard.
148. **Copying a group copies what is inside it.** Copy and Cut take the selected nodes and groups, the nodes inside each selected group, and the groups nested in it; Cut removes all of them. Paste centers the fragment on the pointer (or the middle of the view, or the menu's point) and snaps to the grid when snapping is on; Duplicate puts a copy 24 units down and right of the original, repeatedly if repeated, and leaves the clipboard alone. Both select what they make, and each is one undo step.
149. **Align and distribute are pure geometry (`Arrangement`) run through the model.** Align lines nodes up on an edge or center of the box around all of them; distribute keeps the outer two and equalizes the gaps (three or more nodes). Pinned nodes are measured but not moved, and a node already in place is not recorded. They are in the node menu (Align and Distribute submenus, by how many are selected) and, as buttons, in the inspector's Arrange section for several nodes.
150. **On iPadOS copy, cut and paste are the standard responder actions.** Command-C, Command-X, Command-V, the edit menu and the system's three-finger pinch and spread gestures all reach them; Command-D is a key command. Touch-only users have Copy, Cut, Duplicate and Paste in the context menus. The overlay gives an empty `inputView` so that being first responder (for hardware keys) never raises the software keyboard, which it did whenever a context menu opened, covering half the canvas (found on the iPad simulator).
151. **On macOS Delete is also handled as the delete command.** The Delete key can reach a SwiftUI view as the responder chain's delete command rather than as a key press, so the canvas adds `onDeleteCommand` (the same action as Edit > Delete) beside its key handling. iPadOS reads the key from hardware and was not affected.
152. **Creating a subgraph is a form on the model, over Core's conversion.** `beginCreateSubgraph()` lists what could be exposed (every property of the selected nodes, with its current value) and suggests a name that no existing subgraph has; `createSubgraph(name:promoting:open:)` runs `convertToSubgraphCommand` in the current scope and performs it as one undoable step ("Create Subgraph"), then selects the new instance and, if asked, opens it. The form state lives on the model, not the controller, so the menu, the shortcut and the inspector all open the same form. A blank name or a refusal by the rules (a multi-link input, a missing node) keeps the form open with the reason shown, and changes nothing.
153. **Exposed properties keep their value.** A chosen property becomes a property of the instance whose default is the inner node's current value, so wrapping nodes never changes what the graph computes. Properties are exposed only when creating; changing the interface later is the interface editor's job.
154. **Unpack puts the nodes back where the instance was.** `unpackSubgraph(instance:)` runs Core's `unpackCommand` as one step ("Unpack Subgraph"): inner nodes keep their layout, links to the outside are reconnected, exposed property values are written into the inner nodes, and the new nodes are selected. The definition stays, because other instances may use it.
155. **Where to find it:** Create Subgraph… (Command-G) is in the node context menu and the inspector for one node or several; Unpack Subgraph (Shift-Command-G) and Open Subgraph are in the menu and the inspector when one instance is selected. The form is modal (a dimmed canvas; a tap outside cancels), is fully usable by touch, and works inside a subgraph, where it nests a new one.
156. **Inside a subgraph, an empty selection shows the subgraph, not the graph.** The inspector's Subgraph section has its name and category (both editable), how many nodes use it, a Leave button, and its inputs, outputs and properties, each renamed in place, moved up or down, or removed, with a line saying what it connects to ("feeds Add · a", "from Multiply · result", "sets Scale · Value"), then the inner graph's counts. This answers "where do I see and edit the subgraph's details": click empty canvas inside it.
157. **Interface edits replace the interface and let Core keep instances consistent.** Each is one undo step through `setSubgraphInterface`, performed unscoped. Renaming changes only a display name (ids are stable), so no link outside is touched; reordering changes the port order on instances; removing an entry drops only the links or values that belonged to it, and undo brings them back. A blank name is refused.
158. **Entries are added from the inside.** With a node inside selected, each of its ports and properties has an expose button (filled when exposed): exposing an input adds a subgraph input targeting that port, with its name, type and default; an output adds an output sourced from that port; a property adds a promoted property whose default is the current value. Ids are made unique (`a`, `a_2`). Hiding removes the target, and the entry with it when it has no targets left. The button appears only inside a subgraph.
159. **A converted input is named after the node that feeds it.** An outside output that feeds several of the selected ports already became one input delivering to all of them (so A feeding two wrapped nodes gives one input from A, used by both); it is now named after the feeding node's title ("A") instead of the first inner port's name ("value"). Inputs are ports on the instance, not properties; a property is made only for the ones ticked in the form.
160. **The Create Subgraph name field uses the theme's colors.** The system's rounded field is light, and the form's text is light on dark, so typing was white on white.
161. **Inspector buttons draw in the text color on every platform.** In a form, iPadOS draws a plain button in the accent color (blue on the inspector's gray, hard to read) while macOS uses the normal text color. The inspector's action buttons and icon buttons (Create, Unpack, Open, Leave, Clear, align and distribute, move up and down) now set the label color themselves and dim when disabled. Expose and reset buttons stay in the accent color on purpose, since the color marks "exposed" and "changed".
162. **Run state lives on the editor model, folded from Core's `ExecutionState`.** `GraphEditorModel.executionState` is fed by `apply(_:)` or `observeExecution(_:)` (given `GraphRunner.events()`); it is not part of the graph, history or undo. A node shows a corner badge (running, succeeded, failed, cancelled, skipped, cached; a glyph as well as a color), a progress bar along its bottom edge, and a red or green border while running or failed; a failed node also shows its message under it. Bypassed and never-reached nodes show nothing. The mapping is the pure `NodeRunDecoration`. Not done: animation (a pulsing running badge would need a `TimelineView`), and events for nodes inside a subgraph (the runner reports the instance only, so it carries the aggregate state).
163. **The mini-map is a separate view, `GraphMiniMapView`, placed by the app like the breadcrumb.** It shows every node, the group areas and the viewport; nodes tint by run state and selection, so an error off screen is visible. A press inside the viewport rectangle drags it; a press elsewhere centers the view there. The area shown is the graph plus the viewport, frozen during a drag so the map does not rescale under the pointer. Camera moves are not edits, so they do not touch history.
164. **`NodeProgress` got a public initializer**, so UIs and tests can build progress events.
165. **The custom node drawing hook is a per-type registration on `GraphEditorModel`, not a protocol on `NodeDefinition`.** `NodeDefinition` is in Core, which must not know about drawing; this mirrors `registerWidgetRenderer`. The drawing reserves a fixed-height area in `NodeLayout` (so hit testing, minimum size and drawing agree), is drawn only at full level of detail, and is clipped to its area. Run state is not passed to it yet, since `NodeRunDecoration` is internal.
166. **VoiceOver sees the canvas through `accessibilityChildren`.** The canvas is one drawn view, so `GraphCanvasView` replaces its accessibility children with one element per node (reading order: top to bottom, then left to right), link and group, laid out where they are drawn. They are built only while VoiceOver runs (`accessibilityVoiceOverEnabled`), since they are rebuilt whenever the graph or camera changes. The content is the pure `GraphEditorModel.accessibilityElements()`: a node's label is its title and its value its mode, collapsed/pinned state, run state and the wiring of each port; a link reads "Link from A, out to B, a".
167. **Actions are the same commands as the keyboard and menus.** A node offers Move (Left, Right, Up, Down by one grid cell), Collapse/Expand, Pin/Unpin, Set Mode, Duplicate, Delete, Disconnect All, Open Subgraph and Connect per port; a link offers Add Reroute Point and Delete Link; a group offers Delete. An action first makes its element the selection, then runs the command (`GraphInteractionController.perform(_:on:)`), so every edit is still a history step. Some actions announce the result.
168. **Connecting without dragging is a chooser.** The Connect action calls `GraphEditorModel.beginConnection(from:)`, which lists every port the connection rules allow (`connectionRequest`); `ConnectionChooserOverlay` shows them as buttons and `completeConnection(to:)` connects as one "Connect" step. It works from either end.
169. **Dynamic Type is a text scale on the model.** `GraphEditorModel.textScale` (from `textScale(for: DynamicTypeSize)`, body size over 17 points, capped at 2.5) scales the canvas fonts and the header, port-row, widget-row and minimum-width metrics through `layoutMetrics`, so layout, hit testing and drawing still agree. Port dots and hit radii do not scale. A node's width is not scaled beyond its minimum, so long labels at large sizes are cut with an ellipsis until the user resizes the node. The add-node search and color picker use text styles. Not done: editing widget values by VoiceOver on the canvas (use the inspector), and the inspector's own layout at accessibility sizes has not been checked by eye.
170. **Metal is not needed; the `Canvas` renderer stays.** `ScaleBenchmarkTests` (UI package) measured a 1k, 5k and 10k node grid with a link per node pair (release build, Apple silicon laptop; frames rendered on the CPU through `ImageRenderer`, so a pessimistic stand-in for on-screen drawing). Drawing is culled to the viewport and uses level of detail, so cost follows what is visible, not graph size:

   | Nodes | Cold layout + index | Frame, zoom 1 (77 items) | Frame, zoom 0.3 (792 items) | Frame, zoom 0.1 (all, up to 6.9k items) | Drag step |
   |---|---|---|---|---|---|
   | 1,000 | 4 ms | 5.6 ms | 9.9 ms | 3.4 ms | 2.5 ms |
   | 5,000 | 19 ms | 5.2 ms | 22.5 ms | 18.6 ms | 13.9 ms |
   | 10,000 | 39 ms | 5.2 ms | 23.2 ms | 26.9 ms | 28.6 ms |

   Debug builds are 2 to 6x slower (10k overview 61 ms, drag step 163 ms), which only matters while developing. Worst case is the 10k overview at about 27 ms, and that is a software render; the real frame is composited on the GPU. Revisit Metal only if on-device checks (a physical iPad, launched without the debugger) show an overview that stutters; the first step then would be a cheaper level of detail at very low zoom (nodes as plain rectangles, links batched into one path), which is far smaller than a Metal backend.
171. **The real 10k bottleneck is the per-edit spatial index rebuild, not drawing.** A drag step (move, then query what is visible) costs about 29 ms at 10k nodes in release, over a 16 ms frame, and 14 ms at 5k; it is O(n) as decision 100 predicted. Next step when it matters: update the `SpatialIndex` incrementally from the command (remove and re-insert the moved nodes and their links) instead of rebuilding. Not done yet; no user-facing graph is near 10k, and 1k is 2.5 ms. Link lookups scanning all links (decision 17) did not show up here, since the UI queries through the index.
172. **UI tests find nodes through the same accessibility elements as VoiceOver, switched on by an environment value.** The canvas is one drawn view, so XCUIAutomation saw only "Node graph". `EnvironmentValues.exposesCanvasElements` (public, off by default) builds the elements of decision 166 without VoiceOver; the app shell turns it on for the launch argument `-ExposeCanvasElements`. Frames were checked against a screenshot: each element sits exactly where its node is drawn.
173. **UI tests live in the app project (`NodeGraphAppUITests`, one multiplatform bundle for macOS and iPad), on the demo graph.** Flows covered: select, drag, delete with undo and redo, add from the toolbar search, copy and paste, duplicate, enter and leave a subgraph, and Escape closing the search. A click is used on macOS because a tap does not reach the canvas there; a tap on iPad. Not covered: drawing a link by dragging between ports (port positions are not exposed), pinch and two-finger pan, and Pencil.
174. **On the iPad simulator `typeKey` does not deliver Delete, Escape or Return to the app, though Command shortcuts arrive.** Both the UIKit path (`pressesBegan`) and SwiftUI's `onKeyPress` fail the same way, so this is most likely the harness, but it has not been confirmed on a hardware keyboard. The iPad runs use the long-press menu for Delete and Open Subgraph and skip the Escape test. Check these three keys by hand on a physical iPad with a keyboard.
175. **Read-only is `GraphEditorModel.isEditable`, enforced in the model and mirrored in the UI.** When false, `perform`, `connect`, `group`, `undo` and `redo` throw `GraphEditorModelError.readOnly` and change nothing (`canUndo` and `canRedo` report false), so no path can edit by accident, including future ones. On top of that the UI stops offering edits: `CanvasCommand.isEdit` (an exhaustive switch, so a new command must choose) makes `GraphInteractionController.perform` refuse edit commands and the context menu show them disabled; a press on a port, a resize corner, a widget, a node or a group title selects but never drags into a move, resize or link; widgets and sliders do nothing; double click and link release do not open add-node; VoiceOver offers only Select and Open Subgraph; the inspector's form is disabled. Still allowed: selecting, marquee, pan, zoom, copy, select all, escape, entering and leaving subgraphs, and edits made directly on `editor` followed by `refresh()` (a server change). Choices: button widgets are blocked too, since a read-only viewer should not run actions (a dashboard that wants live buttons can call `onWidgetAction` itself); the inspector's navigation buttons (Open, Leave, problem jump) go disabled with the rest of the form because a disabled parent cannot be partly re-enabled, and the breadcrumb, double click and Return still navigate. Not done: flipping `isEditable` to false in the middle of a drag leaves that drag's edits applied (cancelling it cannot undo), which only matters if a server toggles it live.
176. **Run values are a separate fold from run state: `RunValues` in Core, `GraphEditorModel.runValues` in the UI.** `ExecutionEvent`s stay state-only (decision 162); what a node produced comes from each pass's `TickResult`, folded by `RunValues.apply(_:)` into the latest outputs per node. A node keeps its values until reached again; it loses them when it failed, was muted, disabled or cancelled; an `onTrigger` node that did not fire keeps its last ones. `value(of: link)` is whatever the link's source port published. Root graph only: the runner does not report nodes inside a subgraph instance. The model takes results with `apply(_: TickResult)` or `observeResults(_:)`, separately from `observeExecution(_:)`, and `clearExecutionState()` clears both. Not part of the graph, history or undo.
177. **`GraphValue.summary(limit:)` is the one human-readable form of a value** (Watch, Log, link labels): strings as they are, doubles as Swift prints them, colors as hex, arrays and objects with quoted inner strings and sorted keys, nesting past three levels as `…`, cut to `limit`. Not a serialization format.
178. **Watch, Time and Log are utility nodes; the display is a registered drawing, not a node feature.** `util.watch` takes any value and passes it on as `result` (so it can sit inside a link), and is pure. The editor shows its latest `result` through `NodeContentDrawing.readout(of:)`, which an app registers per type (`NodeContentContext.values` now carries the node's latest outputs); Core and the Nodes pack stay UI-free. `util.time` outputs `elapsed` and `delta` in seconds (numbers) and `tick` (an `.int` on a number port), from `NodeContext.time`, so it is exact in deterministic runs; it is impure. `util.log` writes `label: value` to the node's `swift-log` logger at a chosen level on every pass it runs, then passes the value on; it is impure and logs each pass even when the value has not changed (a continuous run logs at its interval). With nothing connected, Watch and Log output nothing and do not fail. Not done: a log console view in the UI, log-on-change, and a Watch for values inside subgraphs.
179. **A link shows the value it carries while hovered or selected.** A small pill at the link's midpoint (`LinkPath.midpoint()`, halfway by length) at full level of detail, text from `GraphEditorModel.valueLabel(of:)` (summary, 40 characters). There is no pointer hover on iPad, so there it shows on selection. Not done: VoiceOver reading the value.
180. **There is still no per-node state, so stateful nodes are not built.** Executors see only their inputs, properties, time and services (decisions 36 and 44: state lives in feedback links). So the pack gaps that remember something between passes are left out: counter, once, stepper, semaphore, average, accumulate, tendTo. Most can already be wired from `flow.delay` and arithmetic. A per-node state API in `NodeContext` (keyed like decision 73, cleared by `reset()`) would give them proper single nodes, but touches the runner, subgraph scoping, caching and deterministic replay, so it is the owner's call before anything is built on it.
181. **`math.random` is a pure function of seed, pass and node, not a stateful generator.** SplitMix64 over the seed, `ctx.time.tick` and the node's id bytes: the same seed gives the same run, a deterministic run repeats exactly, and every pass gives a new number, with no state. Impure (it reads the pass). Two instances of one subgraph repeat the same sequence, since inner node ids repeat; give each its own seed property if that matters. `min` and `max` may be reversed.
182. **Arrays and objects get port types `array` and `object` (registered by `StandardTypes`), and `.vector` is read as an array of numbers.** The new `DataPack` (array, object, JSON and convert nodes, all pure) takes and returns `GraphValue.array` and `.object`. Index inputs are numbers that must be whole (`1` or `1.0`); an index outside the array fails rather than clamping, except `slice`, which clamps. `object.get` outputs `found` and leaves `value` absent when the key is missing. JSON goes through Core's `JSONValue`: a document with whole doubles writes `1`, which reads back as an int; colors, matrices, data and handles have no JSON form and fail. Registering any pack registers all five standard types, so an existing check of the type list now sees five.
183. **Conversion nodes are explicit; runtime port conversion (decision 61) is still open.** `convert.toNumber` (bool as 0 or 1, text parsed), `convert.toBool` (zero is false; text `true`/`false`/`1`/`0`), `convert.toInt` (rounding chosen: nearest, down, up, toward zero; outputs `.int`; fails past `Int64`).
184. **`flow.both` replaces the wanted "wait for all".** A variadic trigger node cannot know which inputs are linked (an unlinked input never fires), so it would never fire with the spare port. `flow.both` has two fixed trigger inputs and fires when both fired in the same pass; it does not remember an earlier pass (that needs state, decision 180). Chain two for three. The litegraph nodes sequence, stepper, filter and semaphore are not built: sequence has no meaning when all triggers fire in one pass, and filter is `flow.gate`.
185. **Node appearance is optional data on the node, the definition and the port, resolved at draw time.** Core gets three small enums in `NodeAppearance.swift`: `NodeShape` (box, round, card), `NodeTitleMode` (normal, hidden, transparent, autohide) and `PortShape` (circle, square, diamond, arrow, grid). A node's `shape` and `titleMode` are optional overrides; `NodeDefinition.shape` and `titleMode` are optional type defaults; `resolvedShape(in:)` and `resolvedTitleMode(in:)` fall back to round and normal. A port's shape is its own `PortDefinition.shape`, else a diamond for triggers (the existing look), else `PortTypeInfo.shape`, else a circle; the standard `array` type is a grid and `object` a square. All are optional so saved documents, exported definitions and the golden file are unchanged: unset values are not written. Setting them goes through `NodeAttribute.shape` and `.titleMode` (undoable, coalescing per field).
186. **The title mode case is `hidden`, not `none`.** On an optional parameter, `.none` means `Optional.none` (nil), so `titleMode: .none` silently meant "use the default". Found by a test. Avoid `none` as an enum case anywhere that is passed as an optional.
187. **Title modes change drawing only, never layout.** `hidden` and `autohide` (when idle) leave the bar's space empty, so ports, widgets, hit testing and saved sizes stay where they are, and switching mode never moves a link. `autohide` is revealed while the pointer is over the node or it is selected, so on iPad (no hover) it shows on selection. A subgraph instance's badge is part of the title and hides with it. Shapes also draw only: hit testing stays the node's rectangle.
188. **The editor sets appearance from the node menu (Shape and Title Bar submenus, for the whole selection, checking the shared choice) and from the single-node inspector** (a picker each, with Default clearing the override). The multi-node inspector does not show them, since a mixed set of overrides has no single value to show. Not done: a per-slot color override, slot shape editing in the UI (a pack sets it), and VoiceOver actions for them.
189. **Graph variables are read-only parameters declared on the root graph.** `GraphVariable` (name, type, value, summary) lives in `Graph.variables` (ordered by declaration), edited by `addVariable`, `removeVariable` and `updateVariable` commands, so edits are undoable, coalesce per variable and enter the change log. They are root-only (`inSubgraph` refuses them with `invalidScope`), names are unique and not blank, and the file key `variables` is written only when there are some, so existing files and the golden file are unchanged and there is no schema bump (an older build opening a newer file would drop them on save, as with any additive key). The owner chose this over a writable variable: nothing writes a variable during a run, so runs stay deterministic and need no per-node state.
190. **A run sees variables through `NodeContext.variables`, and can override them without editing the graph.** The runner merges each declared value with its overrides and hands the result to every node in the pass, including nodes inside subgraph instances, which read the root's variables by name (a missing name fails the node: `The graph has no variable named "x"`). `GraphRunner(variables:)`, `setVariable(_:to:)` (nil restores the declared value) and `setVariables(_:)` take effect on the next pass. They are strict: an undeclared name throws `VariableOverrideError.undeclared`, and a value of another kind than the declared one (an int for a double) throws `kindMismatch`, since `GraphValue` never converts implicitly (decision 11); a refused `setVariables` changes nothing. `update(graph:registry:)` drops overrides whose variable is gone or changed kind. `reset()` keeps them: they are configuration, not run state. `variables` reports what nodes will see.
191. **`util.variable` is impure.** Its value can change between passes with no input or property changing, so it always runs; pure nodes after it still recompute only when its output changes (tested). Types on variables are informational for now: Core attaches no meaning to `GraphVariable.type`, the editor creates variables as `any`, and the Variable node's output is `any`.
192. **The inspector edits variables with nothing selected at the root:** a row per variable (a number, text or toggle control chosen by the value's kind, other kinds shown as a summary), a remove button, and Add Variable by kind (`VariableEditing`). A value keeps its kind. Rename is not offered, because Variable nodes refer to a variable by name and would be orphaned; add a new one instead. Not done: renaming with updating readers, the summary text in the UI, a diagnostic for a Variable node whose name is not declared (it fails at run time), and variable values in the headless CLI (Phase 6, which can use `variables:`). The document's free-form `metadata` already covers the `extra` part of the audit row.
193. **Per-node state is approved and built (answers decision 180).** An executor reads the state it stored earlier as `ctx.state` (`GraphValue?`) and stores new state by returning `NodeOutputs(..., state:)`; nil leaves it as it was, `.null` forgets it. The runner keeps it in `FrameState.nodeState`, so it follows decision 73: per node, per subgraph instance path, cleared by `reset()`, dropped by `invalidateAll()` for instances, and by `update` for a node whose type changed or that was removed. It is saved only when the node succeeds, so a failed, muted, bypassed or untriggered pass leaves it alone. Deterministic runs repeat exactly, since state is only ever changed in plan order from the previous pass's value. A node that uses state must not be pure: a cached pass never runs the executor, so its update would be lost. Not state: the value is not saved with the document, not shown in the UI, and not available inside the instance node itself.
194. **Stateful node pack.** `flow.counter` (increment, decrement, reset triggers; `start`), `flow.once` (swallows events after the first until reset), `flow.latch` (set and reset; reset wins), `math.accumulate`, `math.average` (window), `math.tendTo` (from 0, by a rate each pass). `flow.latch` stands in for litegraph's semaphore, which is a timed gate that `flow.delay` plus `flow.gate` already express. Stepper and sequence are still not built (decision 184). `flow.both` still only matches triggers from the same pass; latch each input first to remember. Writing a graph variable from a node (`data_store`) is not done: variables stay read-only (decision 189).
195. **Delete with bridge is `CanvasCommand.deleteAndReconnect` (Shift-Delete, and "Delete and Reconnect" in the node menu).** `GraphEditor.bridgeProposals(deleting:in:)` joins every source of the node's first linked input to every target of its first output of the same kind (litegraph pairs only input 0 with output 0; this follows the first linked ports instead, and matches by kind so a trigger never feeds a data port). It only proposes: the UI reads the proposals, removes the node, then connects each, skipping any the rules refuse, all in the one undo step of the delete. With several nodes selected they are bridged in turn, so a chain collapses to one link. The menu item is enabled only if some selected node has something to bridge.
196. **Paste keeping connections is `CanvasCommand.pasteWithConnections` (Command-Shift-V, "Paste with Connections" in the empty-canvas menu).** A fragment now records `inputLinks`: links that fed its nodes from nodes outside it, as they were in the source graph. The field is optional in the file form (written only when non-empty, so the schema version stays 1), and an old fragment reads as having none. `pasteCommand(_:translatedBy:in:keepingConnections:)` restores each one to the new copy of its target when the source node exists in the pasted scope, checking every link against the connection rules on a scratch copy of the graph that already holds the paste; one that is refused (a single-link port already taken, a cycle, a changed type) is skipped rather than failing the paste. Only inputs are restored, as in litegraph: restoring outputs would steal the ports of other nodes' inputs. Plain Paste and Duplicate are unchanged. The sources are matched by node id, so a paste into another document keeps links only if it holds nodes with those ids (a copy of the same document does).
197. **A port type names its default nodes: `PortTypeInfo.defaultProducer` and `defaultConsumer`.** Packs set them, since Core has no domain knowledge. The standard types use `util.number`, `util.bool` and `util.string` as producers and `util.watch` as the consumer (arrays and objects have no constant, so only a consumer). `GraphInteractionController.addDefaultNode(for:)` adds the type's producer beside an input (to its left) or its consumer beside an output (to its right), linked, in one undo step, through the same path as dropping a link on empty canvas. Right-clicking a port puts "Add <Node> Node" at the top of that node's menu (`CanvasCommand.addDefaultNode(for:)`). Not offered: for trigger ports, for types with no default, and for an input that already has a link (adding would replace it silently). Not done: middle-click on a port (litegraph's gesture) and a touch gesture; the menu is the way in for now.
